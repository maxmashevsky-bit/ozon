# Техническое задание Озон

[Исходное ТЗ](Техническое%20задание%20Озон.docx).

GraphQL-сервис для создания и чтения постов, комментариев и ответов. Хранилище выбирается флагом: `memory` или `postgres`. PostgreSQL сохраняет данные между перезапусками; память — до завершения процесса.

## Запуск

Команды выполняются из папки проекта. Для воспроизводимой генерации и тестов `Makefile` использует Go 1.25.0 через `GOTOOLCHAIN` (Go скачает его при необходимости). Для Docker нужен запущенный Docker Engine / Docker Desktop и Compose v2.

### В памяти

```sh
make run
# Или без make:
GOTOOLCHAIN=go1.25.0 go run ./cmd/server -storage=memory
```

Открыть [GraphQL Playground](http://localhost:8080). Endpoint: `POST /query`; `GET /healthz` возвращает 204, пока HTTP-процесс работает. Это liveness-проверка, она не проверяет доступность БД.

### PostgreSQL через Compose

```sh
docker compose up --build -d
# Логи:
docker compose logs -f app
# Остановка с сохранением данных:
docker compose down
```

Приложение доступно по тому же адресу. Порт БД 5432 и порт приложения 8080 привязаны к localhost. Пользователь, пароль и БД в Compose: `ozon`. Это настройки локальной демонстрации.

Для запуска Go-процесса отдельно от контейнера БД:

```sh
docker compose up -d db
export DATABASE_URL='postgres://ozon:ozon@localhost:5432/ozon?sslmode=disable'
GOTOOLCHAIN=go1.25.0 go run ./cmd/server -storage=postgres
```

`.env.example` содержит примеры; сервер сам `.env` не читает. `DATABASE_URL` берётся из окружения. Goose-миграции встроены в бинарник и применяются при старте PostgreSQL-режима. `-migrate=false` отключает их. `-addr` меняет адрес прослушивания, по умолчанию `127.0.0.1:8080`.

### Docker с памятью

```sh
docker build -t ozon-comments:local .
docker run --rm -p 127.0.0.1:8080:8080 ozon-comments:local
```

Если Docker Hub недоступен, базовый образ можно получить через зеркало:

```sh
docker build --build-arg GO_IMAGE=mirror.gcr.io/library/golang:1.25-alpine -t ozon-comments:local .
# Или для Compose:
GO_IMAGE=mirror.gcr.io/library/golang:1.25-alpine docker compose up --build -d
```

Образ запускается от непривилегированного пользователя. Сгенерированные файлы уже находятся в проекте, сборка образа не требует запуска генераторов.

## Личность пользователя

Все чтения публичны. Для mutations передайте HTTP-заголовок `X-User-ID`, например `alice` или `bob`. Допустимы 1–64 ASCII-буквы, цифры, `_` и `-`. В Playground это поле **HTTP HEADERS**:

```json
{"X-User-ID":"alice"}
```

Сервер берёт автора из контекста запроса; аргумента `authorId` у mutations нет. **Это dev-режим: любой клиент может подставить чужой заголовок.** Перед публичным развёртыванием нужна настоящая аутентификация, которая устанавливает подтверждённую личность. Проверка права закрыть комментарии находится в service-слое.

## Примеры GraphQL

Создать пост от имени `alice`:

```sh
curl -s http://localhost:8080/query \
  -H 'Content-Type: application/json' -H 'X-User-ID: alice' \
  --data '{"query":"mutation { createPost(title: \"Первый пост\", text: \"Обсуждаем Go\") { id authorId commentsAllowed } }"}'
```

В следующих примерах подставьте ID, возвращённые сервером. ID — строки в GraphQL, положительные `bigint` в хранилище.

```graphql
# Список постов
query {
  posts(first: 20) {
    edges { cursor node { id title authorId commentsAllowed createdAt } }
    pageInfo { hasNextPage endCursor }
  }
}
```

```graphql
# Пост и первая страница корневых комментариев в одном запросе
query {
  post(id: "1") { id title text authorId commentsAllowed }
  comments(postId: "1", first: 20) {
    edges { cursor node { id text authorId parentId createdAt } }
    pageInfo { hasNextPage endCursor }
  }
}
```

```graphql
# С заголовком X-User-ID: bob
mutation {
  addComment(postId: "1", text: "Корневой комментарий") {
    id postId parentId text authorId
  }
}
```

```graphql
mutation {
  addComment(postId: "1", parentId: "1", text: "Ответ") {
    id parentId text
  }
}
```

```graphql
# Только непосредственные ответы комментария 1
query {
  comments(postId: "1", parentId: "1", first: 20) {
    edges { cursor node { id parentId text } }
    pageInfo { hasNextPage endCursor }
  }
}
```

Следующая страница: передайте `pageInfo.endCursor` предыдущей страницы в `after`:

```graphql
query NextPage($post: ID!, $parent: ID, $cursor: String!) {
  comments(postId: $post, parentId: $parent, first: 20, after: $cursor) {
    edges { cursor node { id text } }
    pageInfo { hasNextPage endCursor }
  }
}
```

```graphql
# Только автор поста (X-User-ID: alice)
mutation {
  setCommentsAllowed(postId: "1", allowed: false) {
    id commentsAllowed
  }
}
```

`allowed: true` открывает комментарии снова. Закрытие запрещает и новые корни, и ответы; старые комментарии остаются доступны. `comment(id: "1")` читает отдельный комментарий.

## Подписки на новые комментарии

Реализовано дополнительное требование ТЗ: `commentAdded(postId: ID!)` через GraphQL over SSE (HTTP POST с `Accept: text/event-stream`). WebSocket-транспорт не включён. Для проверки откройте отдельный терминал:

```sh
curl -N http://localhost:8080/query \
  -H 'Content-Type: application/json' \
  -H 'Accept: text/event-stream' \
  --data '{"query":"subscription { commentAdded(postId: \"1\"){ id postId parentId text authorId } }"}'
```

Теперь добавьте комментарий к посту 1 из другого терминала или Playground. В потоке придёт `event: next` с выбранными полями. Подписки также включают ответы. При закрытом обсуждении подписаться можно, но новые комментарии запрещены. Несуществующий пост возвращает `NOT_FOUND`.

В памяти используется локальный hub. В PostgreSQL триггер отправляет через `NOTIFY` только схему и ID комментария; после commit каждый экземпляр сервиса получает событие через собственное соединение `LISTEN`, читает комментарий и рассылает локальным подписчикам. Откат не создаёт события. Соединение слушателя восстанавливается автоматически; при разрыве активные подписки завершаются, чтобы клиент мог переподключиться.

Доставка **без гарантии**: события не сохраняются, возможны пропуски при разрыве или рестарте. Буфер подписчика — 64 события, максимум 1024 подписки на процесс. Переполнение закрывает подписку и не блокирует запись. Поток живёт до 10 минут, после чего клиент должен открыть новый. Промежуточный прокси также может закрыть неактивный поток; heartbeat не отправляется. После открытия или переподключения перечитайте страницы из хранилища и объедините события по ID, чтобы не полагаться на историю потока. Порядок отображения определяйте по ID.

## Устройство и решения

```text
cmd/server/                   флаги, подключение БД, shutdown
internal/core/                модели, Store/PostTx, service, ошибки, курсоры
internal/graph/               GraphQL-схема, резолверы, gqlgen-код
internal/httpapi/             HTTP, ошибки, ограничения документов, HTTP-тесты
internal/store/memory/        потокобезопасное хранилище
internal/store/postgres/      pgx-транзакции и адаптер
  sql/                        исходные SQL-запросы
  db/                         сгенерированный sqlc-код
internal/events/              ограниченная рассылка подписчикам
internal/store/contract/      общий набор контрактных тестов
internal/testdb/              изолированные схемы интеграционных тестов
migrations/                   встроенные goose-миграции
```

- Бизнес-правила выполняет `core.Service`. Резолверы разбирают ID, вызывают сервис и преобразуют результат. `Store` имеет две реализации. `PostTx` нужен, чтобы бизнес-решение и запись происходили под одной блокировкой.
- В PostgreSQL комментарий ссылается на пост, а `(post_id, parent_id)` — на `(post_id, id)` родителя. Индекс `(post_id, parent_id, id)` обслуживает страницы. Триггер запрещает менять `parent_id`, `post_id` и `id`; родитель создаётся раньше ребёнка. Циклы не возникают. Редактирование и удаление объектов API не предоставляет.
- Глубина хранения не ограничена приложением; дерево не обходится рекурсивно. Отдельно читаются корни и непосредственные ответы. Для раскрытия следующего уровня клиент запрашивает его страницу. Тест создаёт цепочку из 200 ответов.
- Пагинация идёт по возрастанию `id`: `id > after`, `ORDER BY id`, `LIMIT first+1`. `first` по умолчанию 20, допустимо 1–100. Курсор — Base64URL-структура с версией, типом списка, `postId`, `parentId` и последним ID. Чужой курсор отвергается. Клиент должен передавать его как непрозрачную строку; это не подписанный токен доступа.
- Страницы не являются снимком БД между запросами. Новые записи могут появляться при следующем чтении; для обновления списка нужно перечитать первую страницу. ID могут иметь пропуски после откатов. Порядок списка определяется ID, а не временем завершения транзакции.
- Текст комментария ограничен **2000 Unicode-кодовыми точками**, включая пробелы. Это не число байтов и не число видимых графем: emoji с модификаторами может занимать несколько кодовых точек. Текст не обрезается и не нормализуется. Пустой/пробельный текст, некорректный UTF-8 и NUL отвергаются. Заголовок поста ограничен 200, текст поста — 100000 кодовыми точками.
- Добавление комментария и закрытие поста выполняются через `WithinPost`: `SELECT … FOR UPDATE` в PostgreSQL и mutex конкретного поста в памяти. Победившая блокировка определяет порядок. После успешного закрытия последующие добавления запрещены. Изменения разных постов не требуют общей блокировки на всё время операции.
- У `Post` и `Comment` только скалярные поля; неявных запросов из резолверов каждого элемента нет. Поэтому страница постов требует 1 SELECT, корней — 2 (проверка поста + данные), ответов — 3 (ещё проверка родителя). Это проверяется через pgx-трассировщик на страницах размером 1, 50 и 100. Запрос поста вместе с корнями требует 3 SELECT. Цена нескольких страниц под aliases складывается; загрузку полного дерева одним запросом API намеренно не предоставляет.
- Документ содержит одну операцию. Лимиты: 16 уровней полей, 300 раскрытых полей/вхождений фрагментов, стоимость 5000. Каждый узел стоит 1, стоимость полей страницы умножается на `first`. Aliases и повторные фрагменты учитываются, `@skip`/`@include` не уменьшают бюджет. До исполнения действуют также лимит 5000 токенов парсера, тело HTTP до 1 MiB и таймаут операции 10 секунд. Ограничение глубины запроса не ограничивает глубину дерева в БД.
- Ошибки возвращают `extensions.code`: `BAD_USER_INPUT`, `NOT_FOUND`, `FORBIDDEN`, `UNAUTHENTICATED`, `UNAVAILABLE`. Ошибки синтаксиса/схемы имеют стандартные коды gqlgen. SQL и DSN не попадают в клиентские ошибки. Полная ошибка хранилища записывается в серверный журнал.

## Проверки и генерация

```sh
make generate     # sqlc 1.30.0 и gqlgen 0.17.81
make check        # go vet и тесты без БД
make race         # тесты без БД с race detector
make build
```

Интеграционные тесты требуют настоящей PostgreSQL, не используют мок БД и не пропускаются молча при отсутствии подключения. Они создают уникальные схемы и удаляют их после выполнения. Пользователю тестовой БД нужно право `CREATE SCHEMA`. Используйте отдельную тестовую БД:

```sh
docker run --detach --name ozon-test-postgres \
  -e POSTGRES_USER=ozon -e POSTGRES_PASSWORD=ozon -e POSTGRES_DB=ozon_test \
  -p 127.0.0.1:55432:5432 postgres:17-alpine
# Дождаться accepting connections:
docker exec ozon-test-postgres pg_isready -U ozon -d ozon_test

TEST_DATABASE_URL='postgres://ozon:ozon@127.0.0.1:55432/ozon_test?sslmode=disable' make integration

docker rm -f ozon-test-postgres
```

Общий контракт проверяет авторство, запрет комментариев, Unicode, принадлежность родителя, курсоры и страницы, дерево, копирование возвращаемых данных, откат и конкурентные чтения/записи. PostgreSQL-тесты дополнительно проверяют внешние ключи и запрет изменения дерева прямым SQL, ожидание блокировки строки и число SQL-запросов. HTTP-тесты проверяют полный сценарий GraphQL, ошибки, aliases, фрагменты, стоимость, глубину и отсутствие утечки внутренних ошибок. Тесты подписок проверяют SSE, доставку между экземплярами PostgreSQL, отсутствие событий при откате, отмену, переполнение буфера и восстановление LISTEN после принудительного разрыва соединения.

Генераторы закреплены по версии; обновление схемы делается в `schema.graphqls`, SQL — в `sql/queries.sql`, затем `make generate`. Документация инструментов: [gqlgen](https://gqlgen.com/), [sqlc](https://docs.sqlc.dev/en/latest/howto/generate.html), [Goose provider](https://pressly.github.io/goose/documentation/provider/).

## Ограничения

Production-аутентификация, rate limiting, нагрузочные измерения и гарантия снимка между страницами не входят в проект. In-memory ограничен доступной памятью и живёт в одном процессе. Горячий пост сериализует добавления комментариев, чтобы корректно закрывать обсуждение; производительность под нагрузкой не измерялась. Подписки не хранят историю событий и не гарантируют доставку.

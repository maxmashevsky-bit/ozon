# Техническое задание Озон

Go GraphQL-сервис постов и комментариев. [Исходное ТЗ](Техническое%20задание%20Озон.docx), [проверки и соответствие требованиям](docs/verification.md), [измерения](docs/performance/README.md), [архитектурные решения](docs/decisions.md).

## Быстрый запуск

Нужны Go с поддержкой `GOTOOLCHAIN`, Python 3.10+, Docker Engine/Desktop и Compose v2. Makefile закрепляет Go **1.25.0**, gqlgen **0.17.81**, sqlc **1.30.0**. Все команды выполняются из корня репозитория.

```sh
make up           # PostgreSQL, отдельный мигратор, приложение, Nginx
make seed         # 3 демонстрационных поста, корни и ответы; ID сохраняются автоматически
make up-scale     # тот же постоянный volume, три приложения за Nginx
make down         # остановка с сохранением данных
make clean-seed   # явно удалить только записанные командой seed демонстрационные посты
```

API: [localhost:8080/query](http://localhost:8080/query); [Playground](http://localhost:8080). Все опубликованные порты привязаны к loopback. Прямые адреса приложений: 18081–18083, PostgreSQL: 5432. Можно изменить `HTTP_PORT`, `DB_PORT`, `DIRECT_PORT`, `DIRECT_PORT_2`, `DIRECT_PORT_3`. Команда `up` создаёт `.local/` с ключом JWT, конфигурацией Nginx и файлами токенов. Директория исключена из Git и Docker build context, её права — 0700. Секреты монтируются через Compose secrets. При обновлении первоначального стенда сохраняются его пароль и volume `ozon_pgdata`.

При недоступности Docker Hub:

```sh
GO_IMAGE=mirror.gcr.io/library/golang:1.25-alpine \
NGINX_IMAGE=mirror.gcr.io/library/nginx:1.28-alpine make up-scale
```

`make seed` повторно не добавляет уже записанный набор. `clean-seed` проверяет ID, автора `demo` и заголовок; посты пользователя не очищаются. Не удаляйте `.local/` при сохранённом volume: в ней находятся его учётные данные. Для проверки инфраструктуры используются отдельные проекты, БД и volumes.

## Личность и токены

Чтения и подписки публичны. Mutations требуют `Authorization: Bearer <JWT>`. Алгоритм HS256 разрешён явно, проверяются подпись, `exp`, `iss=ozon-local`, `aud=ozon-api`, `sub` и `iat`, если он задан. Автор определяется только по проверенному `sub`; `X-User-ID` в обычном режиме игнорируется. Библиотека: [golang-jwt/jwt v5](https://golang-jwt.github.io/jwt/usage/parse/). Ключ должен содержать не менее 32 байт; локальная автоматизация создаёт криптографически случайный ключ. Срок выдаваемого токена — не более 24 часов.

`make up` и `make seed` автоматически выдают токены `alice`, `bob`, `demo`, `bench` в `.local/*.token`. Для отдельного процесса в памяти:

```sh
make run          # memory, JWT; данные исчезнут при остановке
# В другом терминале:
make tools
bin/token -key-file .local/jwt.key -user alice -ttl 1h > .local/alice.token
```

Утилита `/token` входит и в Docker-образ. Она подписывает локальные демонстрационные токены; это не сервер регистрации или внешний identity provider. Для production понадобится доверенный issuer, ротация ключей и HTTPS. Не передавайте секретный ключ клиенту; клиенту достаточно своего токена.

Пример запроса (не включайте shell tracing `set -x` при работе с токенами):

```sh
curl -s http://localhost:8080/query \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $(cat .local/alice.token)" \
  --data '{"query":"mutation { createPost(title: \"Первый пост\", text: \"Обсуждаем Go\") { id authorId commentsAllowed } }"}'
```

Только явный `AUTH_MODE=dev` разрешает неподтверждённый `X-User-ID`; этот режим не предназначен для общего доступа. Пример: `AUTH_MODE=dev GOTOOLCHAIN=go1.25.0 go run ./cmd/server -storage=memory`. Без токена mutation возвращает `UNAUTHENTICATED`; повреждённый bearer отклоняется даже на чтениях.

## GraphQL

Старые операции сохранены. ID передаются строками. Автор может закрыть и вновь открыть обсуждение; запрет действует одновременно на новые корни и ответы, уже записанные комментарии читаются.

```graphql
query {
  posts(first: 20) {
    edges { cursor node { id title authorId commentsAllowed } }
    pageInfo { hasNextPage endCursor }
  }
  post(id: "1") { id title text }
  comments(postId: "1", first: 20) {
    edges { cursor node { id text parentId } }
    pageInfo { hasNextPage endCursor }
  }
}

mutation { addComment(postId: "1", text: "Корень") { id } }
mutation { addComment(postId: "1", parentId: "1", text: "Ответ") { id } }
mutation { setCommentsAllowed(postId: "1", allowed: false) { commentsAllowed } }
```

`comments(postId, parentId, first, after)` читает только непосредственных детей; без `parentId` — корни. `comment(id)` читает одну запись. Дерево не загружается целиком, глубина хранения не ограничена приложением. Максимум комментария — **2000 Unicode-кодовых точек**, включая пробелы; это не байты и не графемы. Пустой/пробельный текст, NUL и некорректный UTF-8 запрещены. Заголовок поста — до 200, текст — до 100000 кодовых точек.

Добавлена ограниченная пакетная загрузка: до 20 родителей, суммарно до 500 запрошенных элементов. Порядок результата соответствует входу; у каждой ветки свой курсор.

```graphql
query Branches($p: ID!, $a: String, $b: String) {
  commentBranches(postId: $p, branches: [
    {parentId: "1", first: 20, after: $a},
    {parentId: "2", first: 10, after: $b}
  ]) {
    edges { cursor node { id parentId text } }
    pageInfo { hasNextPage endCursor }
  }
}
```

## Контракт пагинации

`first`: 1–100, по умолчанию 20; `after` — непрозрачный Base64URL-курсор с версией, типом списка, постом/родителем и последним ID. Курсор другого списка отвергается. Курсор не даёт прав доступа и не является подписью. SQL использует `id > after ORDER BY id LIMIT first+1`, без OFFSET.

Между страницами нет snapshot: новые записи появляются впереди. После `hasNextPage=false` можно снова читать с последним непустым курсором, чтобы увидеть последующие вставки. В API нет удаления; при записи через API порядок фиксации ID внутри поста совпадает с порядком выдачи ID. Общая блокировка создания постов обеспечивает тот же контракт для списка постов. Поэтому поздняя фиксация меньшего ID не скрывается за уже выданным курсором. Откаты оставляют допустимые пробелы ID. Прямые сторонние записи SQL, обходящие эти блокировки, контракт не поддерживают.

Добавление комментария и изменение `commentsAllowed` берут одну эксклюзивную блокировку поста (`FOR UPDATE`, в memory — mutex). После успешного закрытия последующие добавления запрещены. Разные посты работают параллельно. Сериализация горячего поста сохранена осознанно: [обоснование и измерения](docs/decisions.md).

## SSE и восстановление

`commentAdded(postId)` работает через HTTP POST с `Accept: text/event-stream`, события `next`/`complete`. WebSocket не включён. Служебные строки `: connected`, `: ready`, `: heartbeat` позволяют дождаться регистрации и поддерживают поток; heartbeat по умолчанию раз в 15 секунд. Nginx отключает буферизацию и cache, не повторяет POST на другом upstream.

PostgreSQL-триггер после commit отправляет схему и ID через NOTIFY. Каждый процесс имеет отдельное LISTEN-соединение, читает сохранённую запись и публикует её локальным подписчикам. При потере LISTEN активные потоки закрываются, слушатель переподключается. При переполнении буфера медленный подписчик отключается, запись не ждёт его. Все записи SSE, включая heartbeat, выполняет одна горутина с write deadline.

Контракт — **best effort**, не гарантированная доставка. NOTIFY не хранит историю; возможны пропуски при разрывах, переполнении и рестарте. Для автоматического восстановления есть `commentFeed(postId, first, after)`, читающий все комментарии поста по ID, и готовый клиент:

```sh
make tools
# ID автоматически записаны make seed:
bin/watch -url http://localhost:8080 \
  -post "$(python3 -c 'import json; print(json.load(open(".local/seed.json"))[0])')" \
  -token-file .local/demo.token -duration 10m
```

Клиент открывает SSE, использует события/heartbeat как сигналы перечитать сохранённую ленту, после разрыва переподключается с backoff 100 мс–2 с. Курсор продвигается после обработки записи; один запущенный клиент выводит каждый ID один раз, без растущей карты всех увиденных ID. Это не exactly-once для внешнего обработчика: курсор не сохраняется между перезапусками самого клиента. Mutations автоматически не повторяются; при сетевой неопределённости возможен уже состоявшийся commit.

## Лимиты и масштабирование

| Настройка | Обычный стенд | Три реплики | Область действия |
|---|---:|---:|---|
| `DB_POOL_SIZE` | 20 | 7 на процесс | пул SQL |
| `MAX_OPERATIONS` | 64 | 21 на процесс | одновременно исполняемые HTTP-запросы |
| `RATE_RPS` / `RATE_BURST` | 120 / 240 | 120 / 240 на процесс | подтверждённый пользователь, иначе IP |
| `GLOBAL_RPS` / `GLOBAL_BURST` | 1200 / 240 | **те же 1200 / 240** | общий shared bucket Nginx |
| `MAX_SUBSCRIPTIONS` | 256 | 256 на процесс | активные SSE, standalone default 1024 |
| `SUBSCRIPTION_BUFFER` | 64 | 64 | события на подписчика |
| `REQUEST_TIMEOUT` | 10s | 10s | операция |
| `STREAM_LIFETIME` / `SSE_HEARTBEAT` | 10m / 15s | 10m / 15s | поток |
| `WRITE_TIMEOUT` / `SHUTDOWN_TIMEOUT` | 5s / 10s | 5s / 10s | запись SSE / завершение |
| `GRAPHQL_DEPTH` / `GRAPHQL_FIELDS` / `GRAPHQL_COST` | 16 / 300 / 5000 | те же | документ |
| `MAX_BODY_BYTES` | 1048576 | 1048576 | тело, дополнительно Nginx 1 MiB |

Лимиты предотвращают бесконечные очереди и дают явные 429 `RATE_LIMITED` / 503 `BUSY`; 120 req/s на actor — локальная демонстрационная настройка, не бизнес-SLA. Таблица IP/actor-buckets ограничена 10000 ключами, idle записи удаляются. Глобальный bucket общий для всех workers **одного** Nginx и не умножается при трёх приложениях. Через прямые порты можно обойти LB: они доступны только локально для диагностики. При нескольких Nginx понадобятся распределённый limiter или внешний gateway. Защита не ограничивает общий объём записей на диске.

`TRUSTED_PROXIES` пуст для отдельного бинарника: клиентский XFF игнорируется. Compose явно доверяет приватным Docker CIDR, Nginx перезаписывает XFF реальным peer IP. При развёртывании в общей сети задайте точные доверенные CIDR и закройте прямой доступ к приложениям. Значения env нужно экспортировать перед `make up`; `.env.example` — справочник, скрипты не загружают его автоматически. `APP_CPUS`, `APP_MEMORY`, `DB_POOL_SIZE`, `MAX_OPERATIONS` имеют defaults для профиля 1/3 реплики; их также можно переопределить экспортированными env. Нагрузочный сценарий явно фиксирует сопоставимый бюджет ресурсов независимо от этих пользовательских env.

Одна реплика получает 1 CPU / 512 MiB, три — по 0.34 CPU / 170 MiB, PostgreSQL — 2 CPU / 1 GiB, LB — 0.25 CPU / 64 MiB. Бюджет БД: 3×7 SQL + 3 LISTEN + 2 соединения одного мигратора = 26; при трёх конкурирующих миграторах максимум 30; `max_connections=100`, остаётся большой служебный запас. Мигратор удерживает отдельный session advisory lock на всём вызове Goose, включая создание таблицы версий, и завершается до старта приложений.

`GET /healthz` — liveness 204. `GET /readyz` — 204 только если доступны схема/таблица постов; при недоступности БД или drain — 503. Временный отказ LISTEN виден в `listener_ready`, но не делает недоступными обычные чтения/записи. При SIGTERM процесс закрывает новые запросы и подписки, ждёт активные операции в пределах shutdown deadline, останавливает слушатель и пул.

Стенд демонстрирует распределение нагрузки, **не высокую доступность**: PostgreSQL, Nginx и Docker host остаются едиными точками отказа. Memory поддерживает только один процесс и ограничен его памятью.

## Проверки и наблюдаемость

```sh
make verify       # форматирование, vet, race, воспроизводимость генерации
make verify-full  # выше + Docker build, отдельная PostgreSQL, 3 реплики, системные сценарии
make load-smoke   # 1/3 реплики, шесть сценариев, короткие прогоны
make load-full    # 1/8/32 клиента, 3 повтора, 1/3 реплики; несколько минут
make generate     # редактировать schema.graphqls / queries.sql, затем генераторы
```

Проверки сами выделяют отдельные порты/проекты/volumes, ждут готовности polling с deadline, выдают токены и удаляют свою инфраструктуру. Рабочий volume не используется. Интеграционный helper дополнительно требует имя БД с суффиксом `_test`. Ошибка завершает команду ненулевым кодом; диагностика остаётся в `.artifacts/`. Секретная поддиректория удаляется после прогона и не входит в CI artifacts. `make integration` оставлен для явно переданного `TEST_DATABASE_URL`; обычный путь — `verify-full`.

CI `.github/workflows/verify.yml` автоматически выполняет `verify-full` на push/PR, включая PostgreSQL с race и Docker build. Долгая нагрузка вынесена в ручной workflow `Extended load`. Команды закрепляют toolchain и генераторы; `generate-check` сравнивает содержимое до и после генерации, CI также требует чистый git diff.

`/metrics` доступен на прямом порту приложения (через LB закрыт). Форматы — Prometheus text и JSON с `Accept: application/json`: запросы, ошибки, отказы rate/capacity, активные операции, количество/время SQL, занятость/ожидания/отмены пула, подписчики, медленные отключения, состояние LISTEN, heap и goroutines. Нет ID пользователей/постов в labels. SQL tracer считает SQL-вызовы, включая BEGIN/COMMIT; отдельные SELECT проверяются тестами. Структурированные логи приложения содержат коды ошибок, без SQL, DSN, bearer и сырых ошибок драйвера. Административные логи самой PostgreSQL могут содержать SQL диагностику.

[Отчёт проверок](docs/verification.md) указывает реально выполненные команды. [Отчёт нагрузки](docs/performance/README.md) содержит методику, исходные результаты, разброс и ограничения применимости.

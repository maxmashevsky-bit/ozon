# Архитектурные решения

## Проверенные замечания ревью

На исходном `7ed5139` действительно были доверие произвольному `X-User-ID`, миграции каждого процесса без общей блокировки, сериализация комментариев по посту, отсутствие heartbeat, измерений нагрузки и CI. Для одной страницы N+1 **не было**: 1/2/3 SELECT для постов/корней/ответов независимо от размера страницы. Для 20 веток под aliases получалось 60 SELECT. Перед изменениями прошли `make check`, `make race`, PostgreSQL integration; пользовательских изменений в рабочем дереве не было.

## Модульный монолит

HTTP и gqlgen → `core.Service` → `Store` / `PostTx` → memory или PostgreSQL. Сервис отвечает за авторство, длину текста, область родителя/курсора и правила обсуждения. Адаптеры отвечают за атомарность, индексы и доставку уведомлений. У узлов GraphQL скалярные поля: выбор дополнительных полей узла не вызывает дополнительные запросы. Вспомогательные бинарники migrate/token/watch/bench используют тот же репозиторий; сетевой сервис авторизации, брокер и Redis не добавлялись.

JWT HS256 с проверенной библиотекой даёт проверяемый локальный контекст. Общий секрет означает, что каждый доверенный сервер может выпускать токены; для внешних пользователей нужен отдельный issuer с ротацией/асимметричными ключами. Локальная утилита выдачи не изображает production identity management.

## Горячий пост и порядок commit

`WithinPost` сохраняет `FOR UPDATE` на посте до commit. И закрытие, и insert используют один порядок захвата. FK дополнительно подтверждают принадлежность поста/родителя, ссылки дерева неизменяемы. Отмена контекста откатывает транзакцию; тест с удержанным row lock проверяет deadline.

Заменить exclusive lock на совместимый lock недостаточно. Два insert получат ID 10 и 11, но 11 может завершиться первым. Клиент увидит 11 и продолжит `after=11`; поздний commit 10 будет потерян для этого обхода. Кроме того, upgrade совместимых FK row locks к эксклюзивному lock при закрытии нужно анализировать на взаимоблокировки. Существующая сериализация не имеет такого upgrade и сохраняет контракт закрытия. Цена — ограничение throughput одного поста; результаты вынесены в отчёт. Это осознанный компромисс, а не утверждение о бесконечном масштабировании.

Для `posts` исправлена аналогичная гонка: создание берёт короткий transaction advisory lock **до** выдачи ID. Он глобален для БД, поэтому интенсивное создание постов также сериализуется. Измерения в отчёте относятся к комментариям; нагрузка создания постов отдельно не исследовалась. Следующий шаг при доказанном bottleneck — формальный commit-ordered журнал/курсоры с high-water mark и отдельное измерение, а не ослабление блокировки вслепую.

## Пакетные ветки и индексы

`commentBranches` проверяет пост одним запросом, всех родителей вторым, страницы получает одним LATERAL-запросом с ограничением для каждой ветки. Итого 3 SELECT для 1–20 веток; сохраняются независимые курсоры, лимиты 100 на ветку/500 суммарно. Это заменяет 60 SELECT при раскрытии 20 веток, не загружая всё дерево. Индекс `(post_id,parent_id,id)` обслуживает корни/детей; существующий unique `(post_id,id)` обслуживает recovery feed. Новых индексов и DDL не потребовалось. EXPLAIN ANALYZE на 50 тысячах строк сохранён с отчётом; небольшая таблица постов может обоснованно читаться Seq Scan.

## Миграции и соединения

Отдельный мигратор — нормальный путь. Дополнительный session advisory lock охватывает весь вызов Goose. Причина: `Provider.Up` сначала проверяет pending versions, и создание version table может происходить до встроенной блокировки миграций; гонка была видна в реальном логе первого теста. Резервируем одно соединение для guard, другое для Goose, unlock ограничен timeout. Три одновременных мигратора проверяются на действительно пустой БД. Неизменённые старые migration-файлы сохраняют существующие данные.

## Подписки

NOTIFY — сигнал перечитать состояние, а не журнал доставки. Outbox/брокер понадобятся для более строгих требований, которых нет в исходном ТЗ. Цена текущего решения: каждая реплика читает каждый notification из БД, даже без локального подписчика на этот пост. Это добавляет SQL на запись с ростом числа реплик. При росте сначала измерить эту цену, затем проверять подписанные посты до чтения или пакетировать уведомления; для гарантированного replay вводить outbox с retention и offset.

Recovery feed и ограниченный клиент восстанавливают пропущенные данные без mutation retries и без карты всех ID. Heartbeat будит повторное чтение даже при потерянном уведомлении. Гарантия клиента действует в пределах его запуска и успешной обработки callback; для внешних side effects требуется собственный durable checkpoint/idempotency.

## Рост нагрузки

Сначала наблюдать SQL duration/plan, pool waits, CPU и p95 при реальном распределении постов, подписчиков и объёме данных. Не увеличивать пул пропорционально числу реплик без бюджета соединений. Три доли одного CPU могут проигрывать одному целому CPU из-за throttling, сетевых переходов и лишней обработки NOTIFY. Добавлять ресурсы нужно для измеренного насыщенного компонента; сам факт трёх контейнеров не означает ускорение или HA.

Внешнее развёртывание потребует TLS, доверенного issuer, закрытых прямых портов, управляемых секретов, резервного копирования/восстановления PostgreSQL, отдельного HA для DB/LB и политики хранения. Стенд не содержит эти возможности и не заявляет их наличие.

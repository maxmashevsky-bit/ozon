Оба хранилища выполняют один service-контракт под race detector. PostgreSQL-тесты работают в отдельных схемах одноразовой БД. Сценарий медленного читателя проверяет детерминированное заполнение hub-буфера без чтения; обычные SSE-сокеты, heartbeat и отмена проверяются отдельно. Это не имитация WAN с packet loss.

Дополнительно проверены 1/2/3 SELECT на страницу размера 1/50/100 и 3 SELECT для 1/10/20 веток. Тесты удержанной незавершённой транзакции запрещают более позднему ID обогнать её commit для комментариев и списка постов. JWT-тесты включают отсутствие, повреждение, неверную подпись, expiry, отсутствие обязательного expiry, подмену X-User-ID, чужого и настоящего автора.

## Команды

- `make verify`: gofmt, `go vet`, unit/HTTP/контракт memory с `-race`, повторная sqlc/gqlgen генерация без изменения файлов.
- `make verify-full`: всё выше, Docker build, PostgreSQL integration с `-race`, три приложения, Nginx, перечисленные системные сценарии; инфраструктура удаляется.
- `make load-smoke`: HTTP + проверка GraphQL errors, 1/3 приложения, шесть сценариев.
- `make load-full`: 2 повтора × 8 клиентов × 7 сценариев × 1/3 реплики, измерение 30s после 5s прогрева; ресурсные метрики и pg_stat_statements. Параметры можно менять через `scripts/load.py --duration/--warmup/--repeats/--concurrency/--scenarios/--replicas`.
- `make load-soak`: 64 долгоживущих SSE-подписчика, 180s измерения, 10s прогрева; ресурсные метрики до/после и в процессе.
- `make load-protected`: 32 клиента при штатных защитных лимитах, ожидаемые 429 отдельно от нагрузочной ёмкости.

Точные артефакты успешного финального запуска и нагрузочных прогонов сохраняются в `docs/performance`. Отсутствующие зависимости, неготовый сервис, ошибка GraphQL, sampler или неожиданный HTTP отказ завершают проверку ненулевым кодом. В обычных профилях также проверяется доставка каждого SSE-события каждому подписчику; пропуск, дубликат, обрыв или ошибка подключения делают прогон неуспешным. Защитные лимиты проверяются отдельным профилем, где ожидаемые 429 требуются явно.

## Повторная доработка по ревью от 4 октября 2026

Замечания к `02c790d` подтвердились: прежний бенчмарк принимал потерю SSE при успешных mutations, а `seed` считал непустой список ID завершённым набором. При коротком прогоне без паузы наблюдались одинаковые общие числа ожидаемых и полученных событий, но один пропуск и один дубликат у одного подписчика. Исправленный генератор сохранил [диагностический JSON](performance/reliability-2026-10-04/unthrottled-failure.json) и завершился с кодом 1. Сценарии полного отсутствия, частичной доставки, сочетания пропуска и дубликата, обрыва и ошибки подключения проверены на тестовом HTTP/SSE-сервере по реальному коду выхода команды.

`seed` теперь хранит атомарное состояние с меткой набора и сверяет его с API при каждом запуске. Unit-тесты прерывают выполнение после записи поста, корня, ответа и после commit до записи файла; повторный запуск завершает набор без дубликатов. Старый список ID мигрирует безопасно, в том числе если старый процесс не успел записать ID последнего поста. В отдельной PostgreSQL системной проверке `seed → seed → clean-seed` не меняет пост и комментарии другого автора; очистка отказывается удалять демонстрационный пост, если пользователь оставил под ним комментарий. В постоянной локальной БД повторный `make seed` оставил 3 демонстрационных поста и 18 комментариев; хеши 2 пользовательских постов и 3 комментариев до/после совпали.

Выполнены `make verify-full` после последних Go-тестов (gofmt, vet, race, генерация, сборка, PostgreSQL integration/system), `make load-smoke`, `python3 scripts/load.py full --scenarios read,mixed,large,subscriptions --concurrency 8 --duration 30s --warmup 5s --repeats 2 --replicas 1,3 --no-build`, `python3 scripts/load.py soak --no-build` и `python3 scripts/load.py protected --no-build`. Нагрузочные сценарии используют одноразовые БД; длинный профиль доступен только по ручному workflow, не на каждом push/PR. [Матрица, фактические числа, версии, сырые результаты и ограничения](performance/reliability-2026-10-04/README.md).

Ручная проверка обнаружила два редких сбоя инфраструктурного измерителя: `/metrics` однажды не ответил за 3s при защищённой нагрузке, а `pg_isready` однажды принял ещё не созданную `POSTGRES_DB` за готовую. Теперь краткий timeout ресурса учитывается и повторяется (три подряд завершают прогон ошибкой), а перед запуском приложений проверяется настоящий `SELECT 1` к целевой БД. После исправления `protected` и системная проверка повторены. Предельная публикация без паузы всё ещё может дать потерю/дубликат best-effort SSE; это отображается как неуспешное измерение, а клиентское восстановление проверяется отдельно через сохранённую ленту.

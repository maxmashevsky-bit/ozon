# Повторная проверка нагрузки и SSE — 4 октября 2026

Это новые локальные измерения после замечаний к `02c790d`. [Прежний отчёт](../README.md) описывает старые короткие прогоны и сохранён без замены чисел. Его счётчик сравнивал общее количество SSE-событий, поэтому мог скрыть одновременный пропуск и дубликат у одного подписчика. Теперь критерий сравнивает ID каждого успешно созданного комментария отдельно для каждого подключённого подписчика. Нагрузочный прогон завершается ненулевым кодом при пропуске, дубликате, неожиданном событии/обрыве или ошибке подключения. Это критерий **штатного измерения**, не гарантия доставки production-сервиса: его SSE остаётся best effort; после разрыва клиент восстанавливает ленту через `commentFeed`.

## Среда и матрица

Изолированные Docker Compose-проекты с новой PostgreSQL и fixture: 100 постов, 10 000 корневых комментариев, 40 000 ответов перед каждым случаем. Один вариант: 1 приложение, 1 CPU / 512 MiB. Второй: 3 приложения по 0.34 CPU / 170 MiB (в сумме 1.02 CPU / 510 MiB). Одинаковые PostgreSQL 2 CPU / 1 GiB и Nginx 0.25 CPU / 64 MiB. Нагрузка проходит через Nginx; опубликованные порты доступны только локально. Для ёмкости per-process и LB rate limits подняты до 100 000 RPS; отдельный `protected` использует штатные 120 RPS на actor/process и 1200 RPS общего LB. [Точные параметры и версии для 1 реплики](full/1/metadata.json), [для 3 реплик](full/3/metadata.json).

Запуск `full` был **выбранным подмножеством** профиля: `python3 scripts/load.py full --scenarios read,mixed,large,subscriptions --concurrency 8 --duration 30s --warmup 5s --repeats 2 --replicas 1,3 --no-build`. Итого 4 сценария × 2 повтора × 2 конфигурации = 16 случаев, минимум 9.9 минуты измерения/прогрева/ожидания SSE без пересоздания fixture. `read` сочетает страницу постов и комментариев; `mixed` — чтения с распределёнными добавлениями; `large` создаёт допустимый комментарий из 2000 Unicode-кодовых точек. `subscriptions` публикует с паузой 10 ms, чтобы проверять устойчивую доставку отдельно от предельной скорости записи. Короткий smoke дополнительно покрывает `uniform`, `hot`, `batch` на обеих конфигурациях. Отдельный soak — 64 подписчика, 10s прогрева и 180s измерения на каждой конфигурации, пауза публикации 100 ms. Защитные лимиты проверены отдельным профилем с 32 клиентами, 1s прогрева и 5s измерения на 1 и 3 репликах.

Запуски сделаны с `commit=02c790d4347a91dd0920cd4f58b68b8b97072fbf`, `dirty=true`: исправления ещё не были закоммичены. Метаданные сохраняют SHA-256 всех Go-файлов, версию Go, Docker, PostgreSQL, image ID, время UTC и параметры. Для выбранного `full` SHA-256 `scripts/load.py` в момент запуска — `63766b335023c514af7c4585dab7cb89aa1e81c9fe8e0b7e14b449f6f9e14133`. После длительных измерений дополнены тесты, а в инфраструктурных Python-скриптах обработаны единичный timeout сборщика ресурсов и редкая гонка готовности PostgreSQL при создании новой БД. Исполняемый Go-код сервера и генератора после этих замеров не менялся. `smoke` и `protected` были затем повторены с итоговыми скриптами. Сборка Docker использовала версию сервера из того же рабочего дерева. Локальные необработанные `.artifacts/` содержат посекундные ресурсы и SQL-статистику; здесь сохранены [метаданные](full/1/metadata.json), [результаты](full/1/results.json), [планы запросов](full/1/query-plans.txt) и [сводка ресурсов](full/1/resources-summary.json) каждой конфигурации.

## Обнаруженный прежний ложный успех и границы вывода

При публикации **без паузы** (~683 успешных mutations/s, 8 подписчиков, 2s) новый генератор завершился с кодом 1: `expected_events=10936`, `received_events=10936`, но `missing_events=1` и `duplicate_events=1` у одного подписчика на соседних ID. [Диагностический JSON](unthrottled-failure.json) и [метаданные этого неуспешного запуска](unthrottled-metadata.json). Старый критерий по сумме принял бы это за успех. Тестовый HTTP/SSE-сервер отдельно проверяет фактические коды выхода при полной доставке, полном отсутствии, частичной доставке, сочетании пропуска и дубликата, неожиданном обрыве и ошибке подключения. Намеренный разрыв в системной проверке оценивается критерием восстановления через persisted feed, а не ослаблением обычной проверки доставки.

Все числа относятся к локальному Docker Desktop и заданному fixture. Двух 30-секундных повторов и трёхминутного soak недостаточно для SLA, WAN-потерь, многодневных утечек памяти или поведения при отказе общей PostgreSQL. При высокой интенсивности без ограничения темпа best-effort SSE может терять/повторять сигнал; для важных потребителей нужен recovery feed. Сравнение 1/3 реплик ограничено общим PostgreSQL, Nginx и одним host. Старый отчёт остаётся исторической записью и не переинтерпретируется как результат новой методики.

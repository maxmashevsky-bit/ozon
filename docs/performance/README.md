# Измерения производительности

Исходные результаты до изменения сервиса сохранены в [baseline](baseline/metadata.json): HTTP-замеры, CPU/память, исходник драйвера и параметры. Финальные повторные прогоны выполнены на том же наборе данных: 100 постов, 10000 корней и 40000 ответов. Данные сбрасываются перед каждым прогоном; текущие пользовательские данные не затрагиваются.

Сценарии `scripts/load.py`: read (посты/корни 50/50), mixed (80% чтение корней, 20% распределённых insert), uniform (insert в 100 постов), hot (все insert в один пост), batch (20 веток), subscriptions (1/8/32 SSE читателя, один последовательный publisher). Полный профиль: по 3 повтора, конкурентность 1/8/32, прогрев 1s + измерение 4s; 1 и 3 реплики. Это локальное исследование, не SLA и не длительный soak test.

Перед каждым измерением приложения останавливаются, fixture пересоздаётся только в одноразовой БД, затем приложения запускаются и проходят readiness. Так fixture не засоряет очередь NOTIFY. Лимиты частоты подняты до 100000, чтобы измерять пропускную способность; штатные защитные лимиты проверяются системными тестами.

HTTP-драйвер считает успешными только ответы без GraphQL errors. Latency — от начала запроса до полного чтения ответа, только для успешных операций. Метрики SQL/пула включают прогрев; `successful_rps` и HTTP-перцентили прогрев исключают. SSE delivery измеряется по timestamp издателя в тексте, на часах того же клиента, до чтения события, с ограниченным дренированием до 2s в конце. Для каждого прогона сохранены ожидаемые/полученные события, пропуски и отключения; отсутствие потерь в одном опыте не меняет best-effort контракт.

## Выводы и границы применимости

- Пакетная загрузка даёт конкретный выигрыш для раскрытия дерева. При 32 клиентах прямой HTTP: **186 → 481 успешных запросов/с**, p95 **290 → 116 ms** относительно исходных 20 aliases. В той же новой версии aliases дают 237 RPS, batch — 481. Подтверждённая тестом структурная причина — **60 → 3 SELECT**, с теми же 80 возвращаемыми комментариями и независимыми курсорами.
- В исходном опыте при 8 клиентах распределённая запись дала 1928 RPS, горячий пост — 1089. В полном новом профиле одной реплики медианы — 1689 и 1340. Удержанная блокировка действительно ограничивает горячий пост; она сохранена ради инварианта закрытия и commit-ordered пагинации. Это не оптимизация, замаскированная под улучшение всех операций: например, direct mixed при 8 клиентах снизился с 1513 до 1338 RPS, hot при 32 — с 1689 до 1505.
- Деление примерно одного CPU на три приложения не даёт общего ускорения: при 32 клиентах медиана read **1739 → 1293**, uniform **1805 → 1370**, hot **1442 → 1090** RPS. Для fan-out 32 SSE читателям результат лучше: publisher **227 → 271** RPS, delivery p95 **39.3 → 25.9 ms**. Эти результаты относятся к данному бюджету ресурсов и сценарию.
- У обычной mutation трассировщик фиксирует **5 SQL-вызовов на запрос при одной реплике и 7 при трёх**: BEGIN, блокировка, INSERT, COMMIT и по одному чтению уведомления каждым приложением. Для read — 1.5 в среднем, для batch — 3. В `full/3/hot-c32-r1/sql.json` среднее время LockPost — 86.81 ms, INSERT — 0.62 ms: в этом прогоне доминирует ожидание блокировки, а не сам INSERT. Растут и ожидания свободных соединений. Это объясняет, почему простое увеличение числа процессов/пула не устраняет узкое место одного поста.
- CPU приложений близок к выделенному бюджету на read/batch, а PostgreSQL использует больше CPU на распределённых insert. Дополнительные чтения NOTIFY доказаны счётчиками; влияние дробных CPU-квот и планировщика — обоснованная гипотеза, но CPU-профиль/счётчики throttling здесь не снимались. Следующий эксперимент — целое ядро на реплику, контроль GOMAXPROCS и cgroup throttling, с отдельным отчётом о возросшем бюджете. При высоком write fan-out стоит проверить чтение NOTIFY только для локально подписанных постов или пакетирование, затем измерить снова.
- Прогоны короткие, выполнялись последовательно на общем ноутбуке. Разброс существенный: например, mixed/32/3 — **122–1321 RPS**; выбросы сохранены. Это не изолированный performance lab, нет рандомизации порядка, длительного soak, контроля thermal throttling или внешнего сетевого профиля. Baseline и direct comparison имеют только один повтор, исходная версия не имела pool telemetry. Результаты не определяют production capacity и не доказывают, что небольшие изменения RPS вызваны кодом.

Среда: MacBookAir10,1 (8 логических CPU, 8 GiB RAM), macOS 26.6.2; Docker Linux/aarch64 VM — 8 vCPU, 4108828672 байт RAM. HTTP-драйвер — Go 1.25.0 на хосте, оба сравниваемых server-бинарника — **Go 1.25.14**, PostgreSQL 17.11, Docker 29.5.2. Build info сохранён в [verification/server-build-info.txt](verification/server-build-info.txt) и [verification/baseline-build-info.txt](verification/baseline-build-info.txt). Образ Go при измерении: `mirror.gcr.io/library/golang@sha256:1ae0735f00daffa3aaf1363a5184c0d2dc55c78e3db4ec70241cdac97bf84b59`.

В измеренный отчёт не включён первый пробный smoke с неверной подготовкой данных: он пересоздавал fixture при активных LISTEN и засорял очередь уведомлений. После обнаружения инструмент исправлен, все сохранённые здесь smoke/full/compare выполнены с остановленными на время seed приложениями. Smoke был до коммита и имеет `dirty=true`; полные и direct-прогоны фиксируют чистый `bf7f998` и hash исходников. Последующие изменения касаются документации и инициализации ключа для memory-режима, код сервера и драйвера нагрузки не менялся.
